# How Nodejs Works

```
Client ----------> Server
         Request    (NodeJs)
```

Request made to server. Node js has event queue. 

Firstly requests are queued into event queue . 

Now even loop is a machine which always watches the event queue. 

If event loop get any request in event queue the select that request using fifo(first in first out) principle.

Request can be of two types :
  
  1. Blocking Operations (Sync.. task)
  3. Non- Blockinng Operations (Async.. task)

If the request has `non-blocking operation` then the server process it and sends the response back to the user.

![non-blocking operation in nodejs](./non-blocking.png)

If the request has `blocking operation` then to resolve this request it goes to thread pool. 

Thread pool is a pool of threads . Threads act a worker which work for you . It is resposible for fuilful your blocking operation. If the works completes then it return the result . Then the respose is send back to the user . 

![non-blocking operation in nodejs](./blocking.png)

# Express Middleware

## What is middleware?-can chech security ,middleman,

`Middleware` functions are functions that have access to the request object(req) , the response object(res), and the next middleware function in the application's requests-response cycle. 

The next middleware function commanly denoted by variable `next`.

### Middleware functions can perform:

* Execute any code.
* Make changes to the request and the response objects.
* End the request-response cycle.
* Call the next middleware function in the stack.
* multiple ,iddleware bw req res

If the current middleware is not functioning then it must call next middle ware otherwise request will be left hanging.

MVC Architecture

MVC stands for Model, View, and Controller.

It is an architectural pattern used to separate an application into different parts so that the code becomes organized, maintainable, reusable, and easy to test.

MVC Request Flow:

Client Request
      ↓
    Route
      ↓
  Controller
      ↓
    Model
      ↓
   Database
      ↓
    Model
      ↓
  Controller
      ↓
 View / JSON Response
      ↓
    Client


1. Client

The client is the application or tool that sends a request to the server.

Examples:
- Browser
- React frontend
- Mobile application
- Postman
- Another server

Example request:

POST /api/users

The client may also send data:

{
  "first_name": "Sachin",
  "last_name": "Kumar",
  "email": "sachin@gmail.com",
  "gender": "Male"
}


2. Client Request

A client request is an HTTP message sent by the client to perform an operation.

A request can contain:

- HTTP method
- URL
- Headers
- Body
- Query parameters
- Route parameters

Common HTTP methods:

GET     → Read data
POST    → Create new data
PATCH   → Partially update data
PUT     → Completely update or replace data
DELETE  → Delete data


3. Route

A route maps an HTTP method and URL path to a controller.

The route decides which controller should execute for a particular request.

Example:

router.post("/api/users", createUser);

Here:

POST          → HTTP method
/api/users    → URL path
createUser    → Controller

Other examples:

router.get("/api/users", getAllUsers);

router.get("/api/users/:id", getUserById);

router.patch("/api/users/:id", updateUser);

router.delete("/api/users/:id", deleteUser);

The route should not normally contain database logic.

Its main responsibility is to forward the request to the correct controller.


4. Controller

The controller receives the request from the route.

It acts as a manager between the client and the model.

Main responsibilities of a controller:

- Read req.body
- Read req.params
- Read req.query
- Validate request data
- Call the model
- Handle errors
- Set HTTP status codes
- Send the final response

Example:

const createUser = async (req, res) => {
  try {
    const { first_name, last_name, email, gender } = req.body;

    if (!first_name || !email || !gender) {
      return res.status(400).json({

# Server Side Rendering With EJS
Server-Side Rendering (SSR) is the process of generating the full HTML for a web page on the server before sending it to the client (the user's browser).

Instead of sending an empty HTML shell and relying on JavaScript to build the page in the browser (which is called Client-Side Rendering or CSR), the server does the heavy lifting. When a user requests a URL, the server fetches the necessary data from the database, builds the final HTML document, and sends a fully formed page to the browser.

How SSR Works
The Request: The user's browser requests a webpage (e.g., [yoursite.com/profile](https://yoursite.com/profile)).

Data Fetching: Your server (e.g., a Node.js/Express app) receives the request and grabs the user's data from the database.

HTML Generation: The server passes this data into a templating engine. The engine merges the raw data with an HTML template to generate the final, customized HTML string.

The Response: The server sends this complete HTML document back to the browser.

Display: The browser renders the HTML immediately, meaning the user sees the content much faster.

Why use SSR? It provides fantastic SEO (Search Engine Optimization) because web crawlers easily read fully formed HTML. It also offers a faster "First Contentful Paint," meaning the user sees the actual page content sooner, especially on slower internet connections or low-powered devices.

What is a Templating Engine?
To do SSR effectively, servers need a way to inject dynamic data (like a username or a list of blog posts) into static HTML. Writing string concatenation by hand (e.g., let html = "<h1>" + user.name + "</h1>";) is messy and error-prone.

Templating engines solve this. They allow you to write template files using special syntax. The engine takes these templates, replaces the special syntax with your actual data, and spits out pure HTML.

In the Node.js ecosystem, three of the most popular templating engines are EJS, Pug, and Handlebars.

Comparing EJS, Pug, and Handlebars

Templating Engine Comparison. Source: Medium
Here is a detailed breakdown of how they differ in philosophy and syntax.

1. EJS (Embedded JavaScript)
EJS is highly popular because it doesn't force you to learn a new language. It simply lets you embed raw JavaScript directly into standard HTML using <% %> tags.

Best for: Developers who already know HTML/JS and want a gentle learning curve.

Pros: Very easy to pick up, excellent IDE support, full power of JavaScript inside the template.

Cons: The tags can make the code look visually cluttered if there's a lot of logic.

Example Syntax:

HTML
<!-- EJS looks exactly like HTML, but with embedded tags -->
<div class="user-profile">
  <h1>Welcome, <%= user.name %>!</h1>
  
  <% if (user.isAdmin) { %>
    <p>You have admin privileges.</p>
  <% } else { %>
    <p>Standard user account.</p>
  <% } %>
</div>
2. Pug (formerly Jade)
Pug completely reimagines how you write HTML. It relies on indentation and whitespace instead of closing tags and brackets. It is designed to be as terse and fast to type as possible.

Best for: Developers who hate typing closing tags and prefer clean, minimalist code.

Pros: Extremely readable once you learn it, produces smaller template files, very fast.

Cons: Steep learning curve. If you mess up your indentation (spaces vs. tabs), the template will break.

Example Syntax:

Code snippet
// Pug relies on indentation. No brackets or closing tags!
div.user-profile
  h1 Welcome, #{user.name}!
  
  if user.isAdmin
    p You have admin privileges.
  else
    p Standard user account.
3. Handlebars (.hbs)
Handlebars is an extension of the Mustache templating language. It is a "logic-less" template engine. This means you are heavily restricted from writing actual JavaScript logic (like complex if/else or math operations) directly inside the template.

Best for: Large teams that want strict separation of concerns (keeping business logic strictly on the server and out of the view).

Pros: Forces clean architecture, highly reusable components (called "partials").

Cons: Can be frustrating if you just want to do a quick inline calculation, as you must write custom "helpers" on the server to do it.

Example Syntax:

Handlebars
<!-- Handlebars uses "mustache" brackets {{ }} -->
<div class="user-profile">
  <h1>Welcome, {{user.name}}!</h1>
  
  {{#if user.isAdmin}}
    <p>You have admin privileges.</p>
  {{else}}
    <p>Standard user account.</p>
  {{/if}}
</div>




Here is a breakdown of **Client-Side Rendering (CSR)**, structured as an interview answer so you can confidently compare it to Server-Side Rendering (SSR).

### The Elevator Pitch for CSR

**Client-Side Rendering (CSR)** is an architecture where the server sends a nearly empty HTML document along with a large JavaScript bundle. The user's browser is then responsible for downloading that JavaScript, executing it, fetching any necessary data via APIs, and building the entire user interface right there on the user's device.

When you hear "Single Page Application" (SPA) or frameworks like **React, Vue, or Angular**, they are traditionally using CSR.

---

## 1. How CSR Works (The Flow)

If an interviewer asks you to trace a CSR request, here is the lifecycle:

1. **The Request:** The user navigates to `yoursite.com`.
2. **The Server Response:** The server instantly replies with a bare-bones HTML file (usually containing just a single `<div id="root"></div>`) and a link to a JavaScript bundle.
3. **Downloading:** The browser sees the empty HTML and begins downloading the attached JavaScript file. During this time, the user usually sees a blank screen or a loading spinner.
4. **Execution:** The browser finishes downloading and executes the JavaScript framework (like React).
5. **Data Fetching:** The JavaScript makes asynchronous API calls (AJAX/Fetch) back to a server to get the data it needs (e.g., fetching a list of products in JSON format).
6. **Rendering:** Once the data arrives, the JavaScript dynamically creates the HTML elements and injects them into the DOM. The user finally sees the fully loaded page.

---

## 2. Why Do We Use CSR? (Pros & Cons)

Understanding the trade-offs is crucial for a senior or mid-level engineering interview.

| The Pros (Why use it?) | The Cons (Trade-offs) |
| --- | --- |
| **Lightning-Fast Navigation:** Once the initial JavaScript is loaded, navigating to a new page doesn't require a full browser refresh. The UI just updates instantly (Single Page Application). | **Slower Initial Load:** The First Contentful Paint (FCP) is delayed. The user stares at a blank screen until the JS is downloaded, parsed, and executed. |
| **Rich, App-like UX:** Because the browser handles the UI, you can create highly interactive, smooth experiences with complex animations and state management. | **Poor SEO (Historically):** Because the initial HTML is empty, search engine crawlers struggle to index the site. (Googlebot can execute JS now, but it's still slower and less reliable than SSR). |
| **Decoupled Architecture:** The frontend (React/Vue) and backend (Node/Python/Java) are entirely separate. The backend just serves JSON APIs, meaning you can use the same API for your web app and mobile app. | **Client Device Dependency:** If the user has a cheap smartphone or a slow 3G connection, the heavy JavaScript bundle will make the app feel sluggish and unresponsive. |

---

## 3. The Interview Question: "SSR vs. CSR: Which do we choose?"

If an interviewer gives you a scenario and asks you to pick an architecture, use this rule of thumb:

* **Choose CSR for:** Dashboards, highly interactive web apps (like Figma or Spotify web), internal admin panels, or platforms hidden behind a login screen where SEO does not matter and interactivity is the top priority.
* **Choose SSR for:** E-commerce sites, blogs, news outlets, and marketing pages where SEO is critical, and you need the page to load instantly on slow mobile networks.

> **Bonus Interview Tip: The "Best of Both Worlds"**
> If you want to impress the interviewer, mention that modern web development often uses **"Hybrid" frameworks like Next.js (for React) or Nuxt.js (for Vue).** These frameworks pre-render the initial page load on the server (SSR for fast load and SEO), but once the page loads, it "hydrates" into a standard React/Vue app, giving you the fast CSR navigation for all subsequent clicks.

# 26. Stateful Authentication Interview Answer

Agar interviewer bole:

> **"Explain stateful authentication."**

Tum ye answer de sakte ho:

> "In stateful authentication, the server maintains the user's authentication state in a session store. After successful login, the server creates a session and sends a session identifier to the client, usually through an HTTP-only cookie. On every subsequent request, the browser sends that cookie, and the server uses the session ID to look up the user's session and identify the user. In production, sessions are commonly stored in Redis or another shared persistent store so that sessions survive server restarts and can be shared across multiple application servers."

Ye **interview-ready answer** hai.

# Websocket

# WebSocket

- In general , We send request to the server , server responds to our request and request-response cycle will be closed.
- Communication is single direction. Client request then Server responds (req-res cycle closed)

- Problem :
    - Everytime when user request to the server there is message is available or not. (Chat App)
    - This is called `Polling`. 
    - If message is not available then we are also reuesting to the server
    - Unneccesarly increasing the load to the server.

- Solution :
    - Clinet sent `HTTP` request and tells , i want to make `WebSocket` connection.
    - `Upgrade` Header upgrades `http` connection to `websocket` connection.
    - any one can send message (server <--> Client) (Bidirectional).
    - You don't close the websocket connection unless you want. 
    - WebSocket is just a `protocol`, provides `full-duplex` communication.
    - We don't need `Polling`.


- We use `Socket.io` Library.


# Scale Nodejs App using Cluster

# Scale NodeJS application using the cluster module

- Multiple users concurrently accesing the server then Workload increases.
- When users increases then we can use clusters.
- We distribute the workload on server into multiple apllication threads of nodejs.
- We can make worker threads as no of cpus. 
- When we use cluster it divides assigns the diifferent work with diffirent threads in nodejs in round robin fashion to distribute the workload.

# What is Nginx (Engine-X)?

- NGINX is a powerful web server and uses a non-threaded , event-driven architecture.

- It can also do other important things ,such as `load balancing` , and `HTTP caching`, or be used as a `reverse proxy`.

- Forward Proxy
    - When multiple clients connecting to VPN Sever. And VPN sever is connecting to a server.
    - Only one client for server i.e. VPN.

- Reverse Proxy:
    - When a clinet is connecting a VPN server and that vpn is connecting to multiple servers.
    - Users don't know request will be serve to which server.

- Reverse Proxy:
    - Nginx decides your request will be serve to which server.
- Load Balance - distribute the load.
- Http Cache - make cache to reduce req-res cycle.

- Advantage:
    - Can handle 10000 concurrent requests
    - Cache HTTP requests
    - Act as Reverse Proxy
    - Act as Load Balancer
    - Act as an API Gateway
    - Serve and Cache Static files like images, Videos, etc
    - Handle SSL Certificates

- Prerequisite
    - Docker , Basic Linux Commands , Containerization

# GraphQL

# GraphQL 

- It is  Query Language to make api calls.
- Gives clients the power to ask for exactly what they need and nothing more.

## Problem that GraphQL Solves

- When we make an api call it servers all the data of the particular id from database.
- We use the required data and ignore the others data that we don't want to use or show.
- The problem is every time we call api then it serves all the data which is not required.

- To get the only required data from the database we use GraphQL, It serve the only neccessary that user wants.(reduce over-fetching of data)

- `!` used to define required field.


## What is Axios?
- A Javscript library used for making HTTP requests from web browsers and Node.js applications.

- Features : request and response interception, automatic transformation of JSON data, and the ability to cancel requests.
