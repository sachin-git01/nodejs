# Node.js Interview Notes: npm, Modules & File Handling

These are important Node.js fundamentals for backend developer interviews. I'll explain them in simple English + Hinglish, with definitions, code examples, differences, and interview questions.

# 1. npm (Node Package Manager)

## What is npm?

npm stands for Node Package Manager. It is used to install, manage, and share JavaScript packages and dependencies for Node.js projects.

Simple Hinglish: Jab project mein Express, Multer, Mongoose jaise packages use karne hote hain, unhe install aur manage karne ke liye npm use karte hain.

## A. Important npm commands

| Command                  | Purpose                                       |
| ------------------------ | --------------------------------------------- |
| `npm init`               | Create `package.json` interactively           |
| `npm init -y`            | Create default `package.json`                 |
| `npm install express`    | Install a package                             |
| `npm install`            | Install dependencies listed in the project    |
| `npm uninstall express`  | Remove a package                              |
| `npm update`             | Update packages within allowed version ranges |
| `npm list`               | Display installed packages                    |
| `npm run dev`            | Run the custom `dev` script                   |
| `npm start`              | Run the `start` script                        |
| `npm install -D nodemon` | Install a development dependency              |

## B. What is `package.json`?

`package.json` is the main configuration file for an npm project. It contains project metadata, scripts, and dependency declarations.

Example:

```
{
  "name": "my-node-app",
  "version": "1.0.0",
  "main": "server.js",
  "scripts": {
    "start": "node server.js",
    "dev": "nodemon server.js"
  },
  "dependencies": {
    "express": "^5.0.0"
  },
  "devDependencies": {
    "nodemon": "^3.0.0"
  }
}
```

Key fields:

- `name`: Project name.
- `version`: Project version.
- `main`: Package entry-point metadata.
- `scripts`: Commands that can be run using npm.
- `dependencies`: Packages required by the application.
- `devDependencies`: Packages mainly needed during development.

The version numbers above are examples.

## C. What is `package-lock.json`?

It records the resolved dependency tree and package versions, helping npm install a consistent set of dependencies.

Interview difference:

| `package.json`                                   | `package-lock.json`                                    |
| ------------------------------------------------ | ------------------------------------------------------ |
| Declares dependencies and allowed version ranges | Records exact resolved versions and dependency details |
| Contains scripts and project metadata            | Records the dependency tree                            |
| Usually edited when adding dependencies          | Usually generated or updated by npm                    |

Keep `package-lock.json` in version control for applications so team members can install consistent dependencies.

## D. Dependencies vs devDependencies

Dependencies: Packages needed for the application to run, such as Express or Mongoose.

DevDependencies: Tools mainly needed during development, such as Nodemon, ESLint, or testing tools.

```
npm install express
npm install -D nodemon
```

## E. What is `node_modules`?

It is the directory where npm installs packages and their dependencies.

- Usually excluded from Git.
- Recreated using `npm install`.
- Can become large because packages have their own dependencies.

## F. What is npx?

`npx` can execute package binaries, including binaries from local project dependencies, without requiring you to type their full path.

Example:

```
npx nodemon server.js
```

`npm` primarily manages packages and scripts; `npx` primarily runs package commands.

## G. What is Nodemon?

Nodemon automatically restarts your Node.js application when it detects file changes during development.

```
npm install -D nodemon
```

Add a script:

```
{
  "scripts": {
    "dev": "nodemon server.js"
  }
}
```

Run:

```
npm run dev
```

Without Nodemon, you commonly restart the server manually after code changes.

# 2. Modules in Node.js

## What is a module?

A module is a reusable piece of code that can be imported into another file.

Simple Hinglish: Bade project ko multiple files mein divide karte hain, taaki code reusable, organized aur maintainable rahe.

Node.js has built-in modules, local modules, and third-party modules.

## A. Types of modules

1\. Core modules

Built into Node.js.

Examples: `fs`, `path`, `http`, `os`, `crypto`.

2\. Local modules

Files you create in your project.

Example: `./math.js`, `./user.js`.

3\. Third-party modules

Packages installed through npm.

Examples: Express, Multer, Mongoose.

## B. CommonJS modules — `require()` and `module.exports`

CommonJS is a traditional module system used by Node.js.

### Example 1: Export a function

Create `math.js`:

```
function add(a, b) {
  return a + b;
}

module.exports = add;
```

Create `app.js`:

```
const add = require("./math");

console.log(add(10, 20)); // 30
```

How it works:

1. `module.exports = add` exports the function.
2. `require("./math")` loads the local module.
3. The returned value is stored in `add`.
4. Calling `add(10, 20)` returns `30`.

### Example 2: Export multiple functions

`math.js`:

```
function add(a, b) {
  return a + b;
}

function subtract(a, b) {
  return a - b;
}

module.exports = { add, subtract };
```

`app.js`:

```
const { add, subtract } = require("./math");

console.log(add(5, 3));      // 8
console.log(subtract(5, 3)); // 2
```

Here, an object containing two functions is exported and destructured when imported.

## C. Difference between `module.exports` and `exports`

This is a common interview question.

```
exports.add = (a, b) => a + b;
```

This works because `exports` initially refers to the same export object as `module.exports`.

But:

```
exports = (a, b) => a + b;
```

This does not replace the module's exported value. It only reassigns the local `exports` variable.

To export a single function directly, use:

```
module.exports = (a, b) => a + b;
```

Remember: `module.exports` determines what `require()` returns.

## D. ES Modules — `import` and `export`

ES Modules (ESM) is the standardized JavaScript module system. Node.js supports it alongside CommonJS.

`math.js`:

```
export function add(a, b) {
  return a + b;
}

export default function multiply(a, b) {
  return a * b;
}
```

`app.js`:

```
import multiply, { add } from "./math.js";

console.log(add(2, 3));       // 5
console.log(multiply(2, 3));  // 6
```

To use this syntax in a Node.js project, configure ESM, for example by adding this to `package.json`:

```
{
  "type": "module"
}
```

For relative imports, include the file extension, such as `./math.js`.

## E. CommonJS vs ES Modules

| CommonJS                                 | ES Modules                                                  |
| ---------------------------------------- | ----------------------------------------------------------- |
| `require()`                              | `import`                                                    |
| `module.exports`                         | `export` / `export default`                                 |
| Traditionally common in Node.js projects | Standard JavaScript module system                           |
| Commonly synchronous module loading      | Static imports are resolved by the module system            |
| Often used in `.cjs` files               | Often used in `.mjs` files or `.js` with `"type": "module"` |

Interview answer: Both systems allow us to organize and reuse code. CommonJS uses `require` and `module.exports`, whereas ES Modules use `import` and `export`.

## F. What happens when you use `require()`?

At a high level, Node.js resolves the module, loads and evaluates it, and returns its exported value. CommonJS modules are cached after their first load, so subsequent `require()` calls usually reuse the cached module.

Example:

```
const fs = require("fs");
const path = require("path");
```

These import Node.js built-in modules. You don't need to install them with npm.

# 3. File Handling in Node.js

## What is file handling?

File handling means creating, reading, writing, updating, and deleting files using Node.js.

Node.js provides the built-in `fs` (File System) module for these operations.

Simple Hinglish: Agar humein file mein data save karna, file read karna, ya delete karna hai, to `fs` module use karte hain.

## A. Import the `fs` module

CommonJS:

```
const fs = require("fs");
```

For asynchronous operations using Promises:

```
const fs = require("fs/promises");
```

The `fs/promises` API returns Promises, which work with `async/await`.

## B. Important file-handling methods ⭐

| Method            | Purpose                            |
| ----------------- | ---------------------------------- |
| `fs.readFile()`   | Read a file asynchronously         |
| `fs.writeFile()`  | Create or overwrite a file         |
| `fs.appendFile()` | Add data to a file                 |
| `fs.rename()`     | Rename or move a file              |
| `fs.unlink()`     | Delete a file                      |
| `fs.mkdir()`      | Create a directory                 |
| `fs.readdir()`    | List directory contents            |
| `fs.stat()`       | Get file or directory metadata     |
| `fs.existsSync()` | Synchronously check path existence |

## C. Read a file

Suppose `data.txt` contains:

```
Hello Node.js
```

Using a callback:

```
const fs = require("fs");

fs.readFile("data.txt", "utf8", (err, data) => {
  if (err) {
    console.error(err);
    return;
  }

  console.log(data);
});
```

Output:

```
Hello Node.js
```

- `"utf8"` tells Node.js to return text instead of a raw Buffer.
- `err` contains an error if the operation fails.
- `data` contains the file contents on success.

Without an encoding, `readFile()` returns a `Buffer`.

## D. Write a file

```
const fs = require("fs");

fs.writeFile("data.txt", "Hello World", (err) => {
  if (err) {
    console.error(err);
    return;
  }

  console.log("File written successfully");
});
```

`writeFile()` creates the file if it doesn't exist. If the file already exists, it normally replaces its contents.

## E. Append data to a file

```
const fs = require("fs");

fs.appendFile("data.txt", "\nWelcome to Node.js", (err) => {
  if (err) {
    console.error(err);
    return;
  }

  console.log("Data appended");
});
```

Difference:

- `writeFile()` replaces existing content.
- `appendFile()` adds new content at the end.

## F. Delete a file

```
const fs = require("fs");

fs.unlink("data.txt", (err) => {
  if (err) {
    console.error(err);
    return;
  }

  console.log("File deleted");
});
```

`unlink()` removes a file. It does not remove a non-empty directory; directory operations use other APIs such as `fs.rm()`.

## G. Rename a file

```
const fs = require("fs");

fs.rename("old.txt", "new.txt", (err) => {
  if (err) {
    console.error(err);
    return;
  }

  console.log("File renamed");
});
```

The same API can move a file to another location, subject to filesystem and platform constraints.

## H. Create and read directories

Create a directory:

```
const fs = require("fs");

fs.mkdir("uploads", { recursive: true }, (err) => {
  if (err) {
    console.error(err);
    return;
  }

  console.log("Directory ready");
});
```

List directory contents:

```
fs.readdir("uploads", (err, files) => {
  if (err) {
    console.error(err);
    return;
  }

  console.log(files);
});
```

The `recursive: true` option creates missing parent directories as needed.

## I. File handling with `async/await` ⭐

This is a clean approach frequently used in modern Node.js applications.

```
const fs = require("fs/promises");

async function handleFile() {
  try {
    await fs.writeFile("data.txt", "Hello Node.js");

    const data = await fs.readFile("data.txt", "utf8");
    console.log(data);

    await fs.appendFile("data.txt", "\nNew line");

    console.log("Operations completed");
  } catch (err) {
    console.error("File operation failed:", err.message);
  }
}

handleFile();
```

Why use `async/await`?

- It makes asynchronous code easier to read.
- `try/catch` handles rejected Promises.
- It avoids deeply nested callbacks.

## J. Synchronous vs asynchronous file handling

| Synchronous                                             | Asynchronous                                                   |
| ------------------------------------------------------- | -------------------------------------------------------------- |
| `fs.readFileSync()`                                     | `fs.readFile()`                                                |
| Blocks the Node.js thread until the operation completes | Allows Node.js to continue processing other work while waiting |
| Simple for tiny scripts or startup tasks                | Generally preferred for server request handling                |
| Can reduce server responsiveness under load             | Better suited to concurrent workloads                          |

Example:

```
// Synchronous
const data = fs.readFileSync("data.txt", "utf8");

// Asynchronous
fs.readFile("data.txt", "utf8", (err, data) => {
  if (err) return console.error(err);
  console.log(data);
});
```

Interview tip: Node.js is designed around non-blocking I/O. Avoid synchronous filesystem operations inside frequently executed request handlers because they block the event loop.

## K. What is a Buffer?

A `Buffer` is a Node.js object used to represent binary data, such as image bytes, audio, PDFs, or file contents.

Example:

```
const fs = require("fs");

fs.readFile("photo.png", (err, buffer) => {
  if (err) return console.error(err);

  console.log(Buffer.isBuffer(buffer)); // true
  console.log(buffer.length);
});
```

You can convert a text Buffer to a string:

```
const text = buffer.toString("utf8");
```

For binary files, don't assume that converting the data to UTF-8 text will preserve its contents.

## L. What are Streams?

Streams let Node.js process data piece by piece instead of loading the entire file into memory.

Four common stream types:

- Readable: Reads data.
- Writable: Writes data.
- Duplex: Reads and writes data.
- Transform: Reads data, transforms it, and outputs the result.

Example: Copy a large file using streams.

```
const fs = require("fs");

const source = fs.createReadStream("large.mp4");
const destination = fs.createWriteStream("copy.mp4");

source.on("error", console.error);
destination.on("error", console.error);

destination.on("finish", () => {
  console.log("Copy completed");
});

source.pipe(destination);
```

Streams are useful for large files because they avoid loading the entire file into memory at once. For production pipelines, consider stream error propagation and cleanup as well.

## M. What is the `path` module?

The `path` module provides utilities for handling filesystem paths safely across operating systems.

```
const path = require("path");

console.log(path.basename("/home/user/file.txt"));
// file.txt

console.log(path.extname("photo.png"));
// .png

console.log(path.join("uploads", "photo.png"));
// uploads/photo.png

console.log(path.resolve("uploads"));
// Absolute path to uploads from the current working directory
```

Important methods:

| Method            | Purpose                                |
| ----------------- | -------------------------------------- |
| `path.basename()` | Extract the final path component       |
| `path.dirname()`  | Get the directory portion              |
| `path.extname()`  | Get the extension                      |
| `path.join()`     | Join path segments                     |
| `path.resolve()`  | Resolve segments into an absolute path |

Difference: `path.join()` joins path segments, while `path.resolve()` resolves them into an absolute path, using the current working directory if needed.

# What is Rest Api
A REST API (Representational State Transfer) is an architectural style that allows different software applications to communicate with each other over the internet using HTTP protocols

**Middleware** is software that acts as an intermediary bridging different applications, networks, or layers of an application. In modern technical interviews, the term is asked in two main contexts:

1. **Web / Application Middleware (Most Common):** Functions in an HTTP pipeline that intercept incoming requests before they reach route handlers and outgoing responses before they return to the client.
2. **Distributed System / Enterprise Middleware:** Messaging and communication brokers (e.g., Kafka, RabbitMQ, gRPC) that connect decoupled services.

---

### Core Concept: The Pipeline & Onion Architecture

Web middleware operates on the **Chain of Responsibility** design pattern. Requests travel forward through an ordered series of handlers, and responses travel back in reverse order.

Each middleware component can:

* Execute arbitrary code (logging, telemetry, tracing).
* Mutate the request object (e.g., decoding a JWT and attaching `req.user`).
* **Short-circuit** the pipeline (e.g., returning `401 Unauthorized` without calling downstream handlers).
* Call the next middleware in line via a delegate function (such as `next()`).
* Post-process the response on the unwinding phase.

---

### Common Use Cases

* **Authentication & Authorization:** Validating session cookies or JWTs, verifying role permissions.
* **Logging & Telemetry:** Recording request timing, HTTP methods, client IPs, and status codes.
* **Security Headers & CORS:** Setting headers (`Content-Security-Policy`, `Access-Control-Allow-Origin`, HSTS).
* **Body Parsing & Compression:** Deserializing JSON/URL-encoded payloads, applying Gzip/Brotli compression.
* **Rate Limiting & Throttling:** Tracking IP request quotas using token-bucket or sliding-window algorithms in Redis.
* **Global Error Handling:** Catching unhandled exceptions and formatting standard JSON error payloads.

---

### High-Frequency Interview Questions & Answers

#### 1. What happens if you forget to call `next()`?

The request hangs until the client or gateway times out (typically resulting in a `504 Gateway Timeout`). Execution halts because the framework assumes the middleware either handled the response or initiated an async operation that hasn't finished yet.

#### 2. Why does middleware order matter?

Middleware executes sequentially:

* **Logging & Metrics:** Must be placed near the beginning to capture total request duration.
* **Body Parser:** Must precede routes and auth middleware that inspect payload bodies.
* **Authentication:** Must run before route handlers and protected business logic.
* **Error Handling:** Must be placed at the very end of the pipeline to catch unhandled errors bubbling up from previous layers.

#### 3. How does error-handling middleware differ from standard middleware?

* In frameworks like **Express.js**, an error-handling middleware takes **4 parameters** instead of 3: `(err, req, res, next)`. Express uses arity (`fn.length === 4`) to identify it. Calling `next(err)` skips all remaining standard middleware and jumps straight to the next 4-parameter error handler.
* In **ASP.NET Core** and **Koa**, error handling wraps downstream execution in a `try...catch` block around `await next()`.

#### 4. How do you implement a custom middleware?

```javascript
// Express.js Example: Authentication check
const authenticate = (req, res, next) => {
  const token = req.headers.authorization?.split(' ')[1];
  if (!token) {
    return res.status(401).json({ error: 'Token missing' }); // Short-circuit
  }

  try {
    const decoded = verifyToken(token);
    req.user = decoded; // Attach metadata for downstream handlers
    next();             // Pass control to next middleware
  } catch (err) {
    next(err);          // Pass error to global error handler
  }
};

```

### Comparison: Framework Middleware Implementations

| Framework / Language | Pattern | Key Characteristics |
| --- | --- | --- |
| **Express (Node.js)** | Callback / Linear chain | Uses `(req, res, next)`. Order of registration in `app.use()` dictates execution sequence. |
| **Koa / Fastify (Node.js)** | Async / Onion model | `await next()` allows explicit pre-processing before `next()` and post-processing after it resolves. |
| **Django (Python)** | Class / Hook-based | Implements `process_request`, `process_view`, `process_exception`, and `process_response`. |
| **ASP.NET Core (C#)** | Request Delegate Pipeline | Configured via `app.Use(...)` returning a `Task`. Strict bidirectional onion traversal. |
| **Go (`net/http`)** | Function wrapper | Functions taking and returning `http.Handler` (`func(http.Handler) http.Handler`). |

# Http Status Code


```javascript
HTTP status codes are 3-digit integers issued by a server in response to a client's request, categorized into 5 distinct classes by their leading digit.

---

### Status Code Classes (Quick Reference)

* **1xx (Informational):** Request received, continuing process.
* **2xx (Success):** Action successfully received, understood, and accepted.
* **3xx (Redirection):** Further action needed to complete the request.
* **4xx (Client Error):** The request contains bad syntax or cannot be fulfilled.
* **5xx (Server Error):** The server failed to fulfill an apparently valid request.

---

### High-Frequency Interview Codes

| Code | Name | Typical Production Scenario |
| --- | --- | --- |
| **200** | **OK** | Standard success for `GET`, `PUT`, `PATCH`. Returns data in the response body. |
| **201** | **Created** | Successful `POST`. New resource created; typically includes a `Location` header. |
| **204** | **No Content** | Successful `DELETE` or `PUT`. Action completed, response body is intentionally empty. |
| **301** | **Moved Permanently** | Permanent URL migration. Browsers and search engines cache this redirect indefinitely. |
| **302** | **Found** | Temporary redirect. Search engines do not update the original URL index. |
| **304** | **Not Modified** | Conditional request (`If-None-Match` / `ETag`). Informs the browser to use its local cache; body is empty. |
| **400** | **Bad Request** | Malformed request body, invalid JSON syntax, or failed payload validation. |
| **401** | **Unauthorized** | Missing or invalid authentication token/credentials. (Literally means *Unauthenticated*). |
| **403** | **Forbidden** | User is authenticated, but lacks permissions/roles to access the resource. |
| **404** | **Not Found** | Resource URI does not exist (or hidden intentionally for security). |
| **409** | **Conflict** | State collision (e.g., trying to register an email address that already exists). |
| **422** | **Unprocessable Entity** | Syntactically valid JSON/body, but fails semantic domain validation rules. |
| **429** | **Too Many Requests** | Rate limit exceeded. Usually paired with a `Retry-After` header. |
| **500** | **Internal Server Error** | Unhandled exception or fatal runtime crash on the server. |
| **502** | **Bad Gateway** | Reverse proxy (NGINX, Cloudflare) received an invalid response from upstream (Node, Django). |
| **503** | **Service Unavailable** | Server overloaded or undergoing planned maintenance. |
| **504** | **Gateway Timeout** | Upstream application took too long to respond to the reverse proxy/load balancer. |

---

### Top Interview Dilemmas & Trap Questions

#### 1. `401 Unauthorized` vs. `403 Forbidden`

* **`401` = Who are you? (Authentication failure):** The client failed to provide valid credentials. The response must include a `WWW-Authenticate` header challenge.
* **`403` = You can't be here. (Authorization failure):** The server knows the user's identity, but the user does not have permission to execute the action. Sending credentials again will not change the outcome.

#### 2. `301 Moved Permanently` vs. `302 Found` vs. `307/308`

* **Method mutating (`301` / `302`):** Historically, browsers would switch a non-GET method (`POST`) to a `GET` when following these redirects.
* **Strict method preserving (`307 Temporary Redirect` / `308 Permanent Redirect`):** Guarantees that the HTTP method and request body remain identical when following the redirect (e.g., a `POST` must be resent as a `POST`).

#### 3. `502 Bad Gateway` vs. `504 Gateway Timeout`

* **`502 Bad Gateway`:** The reverse proxy reached the upstream server, but the upstream server died, dropped the connection, or returned an unreadable response.
* **`504 Gateway Timeout`:** The upstream server accepted the connection but took longer to finish than the proxy's configured read timeout threshold.

#### 4. `400 Bad Request` vs. `422 Unprocessable Entity`

* Use **`400`** when the request is syntactically broken (e.g., corrupted JSON, missing required headers, malformed URL query syntax).
* Use **`422`** (standardized in RFC 4918) when the JSON is valid, but the data fails domain logic constraints (e.g., `age` is a negative number or `password` is shorter than 8 characters).

MVC Architecture

MVC stands for Model, View, and Controller.

It is an architectural pattern used to separate an application into different parts so that the code becomes organized, maintainable, reusable, and easy to test.

MVC Request Flow:

Client Request
      ↓
    Route
      ↓
  Controller
      ↓
    Model
      ↓
   Database
      ↓
    Model
      ↓
  Controller
      ↓
 View / JSON Response
      ↓
    Client


1. Client

The client is the application or tool that sends a request to the server.

Examples:
- Browser
- React frontend
- Mobile application
- Postman
- Another server

Example request:

POST /api/users

The client may also send data:

{
  "first_name": "Sachin",
  "last_name": "Kumar",
  "email": "sachin@gmail.com",
  "gender": "Male"
}


2. Client Request

A client request is an HTTP message sent by the client to perform an operation.

A request can contain:

- HTTP method
- URL
- Headers
- Body
- Query parameters
- Route parameters

Common HTTP methods:

GET     → Read data
POST    → Create new data
PATCH   → Partially update data
PUT     → Completely update or replace data
DELETE  → Delete data


3. Route

A route maps an HTTP method and URL path to a controller.

The route decides which controller should execute for a particular request.

Example:

router.post("/api/users", createUser);

Here:

POST          → HTTP method
/api/users    → URL path
createUser    → Controller

Other examples:

router.get("/api/users", getAllUsers);

router.get("/api/users/:id", getUserById);

router.patch("/api/users/:id", updateUser);

router.delete("/api/users/:id", deleteUser);

The route should not normally contain database logic.

Its main responsibility is to forward the request to the correct controller.


4. Controller

The controller receives the request from the route.

It acts as a manager between the client and the model.

Main responsibilities of a controller:

- Read req.body
- Read req.params
- Read req.query
- Validate request data
- Call the model
- Handle errors
- Set HTTP status codes
- Send the final response

Example:

const createUser = async (req, res) => {
  try {
    const { first_name, last_name, email, gender } = req.body;

    if (!first_name || !email || !gender) {
      return res.status(400).json({
        message: "Required fields are missing"
      });
    }

    const user = await User.create({
      first_name,
      last_name,
      email,
      gender
    });

    return res.status(201).json({
      message: "User created successfully",
      user: user
    });

  } catch (error) {
    return res.status(500).json({
      message: error.message
    });
  }
};

In this example, the controller:

1. Reads the request body.
2. Validates the data.
3. Calls the User model.
4. Receives the saved user.
5. Sends a JSON response to the client.


5. Model

The model handles data-related logic and database operations.

The model defines:

- Data structure
- Data types
- Validation rules
- Database collection
- CRUD operations

Example using Mongoose:

6. Schema

A schema defines the structure and rules of a document.

Example:

const userSchema = new mongoose.Schema({
  first_name: {
    type: String,
    required: true
  }
});

The schema tells Mongoose:

- Which fields exist
- What their data types are
- Which fields are required
- Which fields must be unique
- What validation rules should be applied


7. Model vs Schema

# Server Side Rendering With EJS
Server-Side Rendering (SSR) is the process of generating the full HTML for a web page on the server before sending it to the client (the user's browser).

Instead of sending an empty HTML shell and relying on JavaScript to build the page in the browser (which is called Client-Side Rendering or CSR), the server does the heavy lifting. When a user requests a URL, the server fetches the necessary data from the database, builds the final HTML document, and sends a fully formed page to the browser.

How SSR Works
The Request: The user's browser requests a webpage (e.g., [yoursite.com/profile](https://yoursite.com/profile)).

Data Fetching: Your server (e.g., a Node.js/Express app) receives the request and grabs the user's data from the database.

HTML Generation: The server passes this data into a templating engine. The engine merges the raw data with an HTML template to generate the final, customized HTML string.

The Response: The server sends this complete HTML document back to the browser.

Display: The browser renders the HTML immediately, meaning the user sees the content much faster.

Why use SSR? It provides fantastic SEO (Search Engine Optimization) because web crawlers easily read fully formed HTML. It also offers a faster "First Contentful Paint," meaning the user sees the actual page content sooner, especially on slower internet connections or low-powered devices.

What is a Templating Engine?
To do SSR effectively, servers need a way to inject dynamic data (like a username or a list of blog posts) into static HTML. Writing string concatenation by hand (e.g., let html = "<h1>" + user.name + "</h1>";) is messy and error-prone.

Templating engines solve this. They allow you to write template files using special syntax. The engine takes these templates, replaces the special syntax with your actual data, and spits out pure HTML.

In the Node.js ecosystem, three of the most popular templating engines are EJS, Pug, and Handlebars.

Comparing EJS, Pug, and Handlebars

Templating Engine Comparison. Source: Medium
Here is a detailed breakdown of how they differ in philosophy and syntax.

1. EJS (Embedded JavaScript)
EJS is highly popular because it doesn't force you to learn a new language. It simply lets you embed raw JavaScript directly into standard HTML using <% %> tags.

Best for: Developers who already know HTML/JS and want a gentle learning curve.

Pros: Very easy to pick up, excellent IDE support, full power of JavaScript inside the template.

Cons: The tags can make the code look visually cluttered if there's a lot of logic.

Example Syntax:

HTML
<!-- EJS looks exactly like HTML, but with embedded tags -->
<div class="user-profile">
  <h1>Welcome, <%= user.name %>!</h1>
  
  <% if (user.isAdmin) { %>
    <p>You have admin privileges.</p>
  <% } else { %>
    <p>Standard user account.</p>
  <% } %>
</div>
2. Pug (formerly Jade)
Pug completely reimagines how you write HTML. It relies on indentation and whitespace instead of closing tags and brackets. It is designed to be as terse and fast to type as possible.

Best for: Developers who hate typing closing tags and prefer clean, minimalist code.

Pros: Extremely readable once you learn it, produces smaller template files, very fast.

Cons: Steep learning curve. If you mess up your indentation (spaces vs. tabs), the template will break.

Example Syntax:

Code snippet
// Pug relies on indentation. No brackets or closing tags!
div.user-profile
  h1 Welcome, #{user.name}!
  
  if user.isAdmin
    p You have admin privileges.
  else
    p Standard user account.
3. Handlebars (.hbs)
Handlebars is an extension of the Mustache templating language. It is a "logic-less" template engine. This means you are heavily restricted from writing actual JavaScript logic (like complex if/else or math operations) directly inside the template.

Best for: Large teams that want strict separation of concerns (keeping business logic strictly on the server and out of the view).

Pros: Forces clean architecture, highly reusable components (called "partials").

Cons: Can be frustrating if you just want to do a quick inline calculation, as you must write custom "helpers" on the server to do it.

Example Syntax:

Handlebars
<!-- Handlebars uses "mustache" brackets {{ }} -->
<div class="user-profile">
  <h1>Welcome, {{user.name}}!</h1>
  
  {{#if user.isAdmin}}
    <p>You have admin privileges.</p>
  {{else}}
    <p>Standard user account.</p>
  {{/if}}
</div>




Here is a breakdown of **Client-Side Rendering (CSR)**, structured as an interview answer so you can confidently compare it to Server-Side Rendering (SSR).

### The Elevator Pitch for CSR

**Client-Side Rendering (CSR)** is an architecture where the server sends a nearly empty HTML document along with a large JavaScript bundle. The user's browser is then responsible for downloading that JavaScript, executing it, fetching any necessary data via APIs, and building the entire user interface right there on the user's device.

When you hear "Single Page Application" (SPA) or frameworks like **React, Vue, or Angular**, they are traditionally using CSR.

---

## 1. How CSR Works (The Flow)

If an interviewer asks you to trace a CSR request, here is the lifecycle:

1. **The Request:** The user navigates to `yoursite.com`.
2. **The Server Response:** The server instantly replies with a bare-bones HTML file (usually containing just a single `<div id="root"></div>`) and a link to a JavaScript bundle.
3. **Downloading:** The browser sees the empty HTML and begins downloading the attached JavaScript file. During this time, the user usually sees a blank screen or a loading spinner.
4. **Execution:** The browser finishes downloading and executes the JavaScript framework (like React).
5. **Data Fetching:** The JavaScript makes asynchronous API calls (AJAX/Fetch) back to a server to get the data it needs (e.g., fetching a list of products in JSON format).
6. **Rendering:** Once the data arrives, the JavaScript dynamically creates the HTML elements and injects them into the DOM. The user finally sees the fully loaded page.

---

## 2. Why Do We Use CSR? (Pros & Cons)

Understanding the trade-offs is crucial for a senior or mid-level engineering interview.

| The Pros (Why use it?) | The Cons (Trade-offs) |
| --- | --- |
| **Lightning-Fast Navigation:** Once the initial JavaScript is loaded, navigating to a new page doesn't require a full browser refresh. The UI just updates instantly (Single Page Application). | **Slower Initial Load:** The First Contentful Paint (FCP) is delayed. The user stares at a blank screen until the JS is downloaded, parsed, and executed. |
| **Rich, App-like UX:** Because the browser handles the UI, you can create highly interactive, smooth experiences with complex animations and state management. | **Poor SEO (Historically):** Because the initial HTML is empty, search engine crawlers struggle to index the site. (Googlebot can execute JS now, but it's still slower and less reliable than SSR). |
| **Decoupled Architecture:** The frontend (React/Vue) and backend (Node/Python/Java) are entirely separate. The backend just serves JSON APIs, meaning you can use the same API for your web app and mobile app. | **Client Device Dependency:** If the user has a cheap smartphone or a slow 3G connection, the heavy JavaScript bundle will make the app feel sluggish and unresponsive. |

---

## 3. The Interview Question: "SSR vs. CSR: Which do we choose?"

If an interviewer gives you a scenario and asks you to pick an architecture, use this rule of thumb:

* **Choose CSR for:** Dashboards, highly interactive web apps (like Figma or Spotify web), internal admin panels, or platforms hidden behind a login screen where SEO does not matter and interactivity is the top priority.
* **Choose SSR for:** E-commerce sites, blogs, news outlets, and marketing pages where SEO is critical, and you need the page to load instantly on slow mobile networks.

> **Bonus Interview Tip: The "Best of Both Worlds"**
> If you want to impress the interviewer, mention that modern web development often uses **"Hybrid" frameworks like Next.js (for React) or Nuxt.js (for Vue).** These frameworks pre-render the initial page load on the server (SSR for fast load and SEO), but once the page loads, it "hydrates" into a standard React/Vue app, giving you the fast CSR navigation for all subsequent clicks.

## 1. System Design Context: The Authentication Dilemma

In backend interviews, discussions around authentication typically start with the trade-offs between two architectural models:

### Stateful Architecture (Session ID stored in Database)

* **Flow:** The user logs in $\rightarrow$ the server creates a Session ID and stores it in the database $\rightarrow$ the client receives only the Session ID.
* **Interview Trap:** *"Why not just persist session IDs in a centralized database to prevent session loss on server restarts?"*
1. **Latency Penalty:** Every incoming request requires an active database query to validate the session. If the database lives on a separate instance, port, or cloud region, this introduces a $200\text{--}300\text{ ms}$ round-trip overhead per request.
2. **Cost Escalation (Cloud I/O Pricing):** Managed databases (e.g., AWS RDS, DynamoDB, MongoDB Atlas) bill per Read/Write operation. A user refreshing the landing page 10 times triggers 10 unnecessary read operations.
3. **Horizontal Scaling Chokepoint:** As concurrent traffic grows, database read throughput becomes the primary system bottleneck.



### Stateless Architecture (JWT / Cryptographic Tokens)

* **Flow:** The server encodes user identity data (Payload: `id`, `email`) into a token and signs it cryptographically using a private secret key.
* **Advantage:** The server does not maintain an active session store or query a database for authentication. Validating a token is an $O(1)$ CPU-bound cryptographic verification.

## 2. Core Concepts: What are Cookies and How Do They Work?

A cookie is a small key-value data pair generated by a web server and stored locally inside the client's browser.

```
[Browser / Client]                                       [Node.js / Express Server]
        │                                                          │
        │─── 1. POST /login (Credentials) ────────────────────────>│
        │                                                          │ ── Validates & Generates JWT
        │<── 2. Response + Header: [Set-Cookie: uid=JWT; ...] ─────│
        │                                                          │
(Stores cookie in domain jar)                                      │
        │                                                          │
        │─── 3. GET /dashboard (Header: [Cookie: uid=JWT] auto) ──>│
        │                                                          │ ── Middleware reads req.cookies
        │<── 4. Protected Response / HTML ─────────────────────────│

```

### The 3 Core Cookie Rules

1. **Server-Driven Initialization:** Cookies are created at the server's instruction. The server sends a `Set-Cookie` response header.
2. **Automatic Browser Transmission:** Once stored, the browser automatically attaches the cookie to the `Cookie` request header for **every subsequent request** sent to that origin. No manual client-side code is needed.
3. **Domain Boundary & Isolation:** Cookies are bound to specific origins. A cookie set by `facebook.com` will never be dispatched to `piyushgarg.dev`. Without this isolation, malicious websites could intercept session tokens from other services.

---

## 3. Production Security Flags & Cookie Options

In Express, options are passed directly to `res.cookie(name, value, [options])`:

| Property | Description | Interview & Security Significance |
| --- | --- | --- |
| **`httpOnly`** | Blocks client-side JavaScript (`document.cookie`) from accessing the cookie. | **XSS Mitigation:** Even if an attacker executes malicious injected scripts, they cannot read or exfiltrate the token. |
| **`secure`** | Forces transmission exclusively over encrypted HTTPS connections. | **MITM Defense:** Prevents cookie theft via packet sniffing over plain HTTP. |
| **`domain`** | Defines the domain scope where the cookie is accessible. | **SSO Architecture:** Setting `domain: ".google.com"` shares the cookie across `mail.google.com`, `drive.google.com`, and `youtube.com`. |
| **`expires` / `maxAge**` | Defines the lifespan of the cookie. | Omission creates a **Session Cookie** (cleared upon closing the browser/tab). Inclusion creates a **Persistent Cookie**. |
| **`sameSite`** | Accepts `Strict`, `Lax`, or `None`. | **CSRF Mitigation:** Governs whether cookies are dispatched with cross-site requests. |

## 4. Architectural Comparison: Cookies vs. Authorization Bearer Token

A frequent system design question: *"Should authentication tokens be passed via Cookies or the Authorization Header?"*

```
                    ┌────────────────────────────┐
                    │    Client Request Type     │
                    └─────────────┬──────────────┘
                                  │
                 ┌────────────────┴────────────────┐
                 ▼                                 ▼
      [Browser-Only Web App]            [Mobile App / Microservices / Public API]
                 │                                 │
                 ▼                                 ▼
         Use HttpOnly Cookie            Use Authorization: Bearer <token>
  (Auto-handled, Safe from XSS)        (Flexible, Platform-independent, Safe from CSRF)

```

| Parameter | Cookie-Based Auth | Bearer Token Auth |
| --- | --- | --- |
| **Transmission Mechanism** | `Set-Cookie` header $\rightarrow$ Browser auto-attaches | Sent via response body $\rightarrow$ Client explicitly attaches header |
| **Header Format** | `Cookie: uid=xyz123` | `Authorization: Bearer xyz123` |
| **Storage Location** | Browser Cookie Jar | `localStorage` / `sessionStorage` (Web) or Secure Keyring (Mobile) |
| **Platform Compatibility** | **Browser-only.** Mobile and desktop apps do not have native cookie jars. | **Universal:** Works across React, iOS, Android, Flutter, Postman, CLI, and microservices. |
| **Primary Attack Vector** | **CSRF** (Cross-Site Request Forgery) | **XSS** (Cross-Site Scripting, if stored in `localStorage`) |
| **CORS Overhead** | Higher (Requires `credentials: 'include'`, explicit origins). | Lower (Easily passed across different domains and API gateways). |

## 5. Express.js Implementation Patterns

### Pattern A: Cookie-Based Authentication

```javascript
import express from "express";
import cookieParser from "cookie-parser";
import jwt from "jsonwebtoken";

const app = express();
const JWT_SECRET = "super_secret_key";

app.use(express.json());
app.use(cookieParser());

// 1. Login Route: Issue Cookie
app.post("/api/login", (req, res) => {
  const { email, password } = req.body;
  // Authenticate user credentials against database...
  const user = { id: "usr_101", email };

  const token = jwt.sign(user, JWT_SECRET, { expiresIn: "1d" });

  res.cookie("uid", token, {
    httpOnly: true, // Prevents XSS script access
    secure: process.env.NODE_ENV === "production",
    sameSite: "strict", // Prevents CSRF
    maxAge: 24 * 60 * 60 * 1000 // 1 day in milliseconds
  });

  return res.json({ message: "Login successful" });
});

// 2. Cookie Verification Middleware
function restrictWithCookie(req, res, next) {
  const token = req.cookies?.uid;
  if (!token) {
    return res.status(401).json({ error: "Unauthorized: Missing authentication cookie" });
  }

## 6. Interview FAQ & Rapid-Fire Questions

**Q1. What is the significance of the word "Bearer" in the `Authorization` header?**

* **Answer:** It defines the authentication scheme under **RFC 6750 (OAuth 2.0)**. "Bearer" literally means "the bearer of this token." It indicates that whoever holds the token is granted access to the protected resource without having to provide cryptographic proof of possession.

**Q2. Why is storing a JWT in `localStorage` considered worse than an `HttpOnly` cookie?**

* **Answer:** `localStorage` is completely accessible via client-side JavaScript. If the application contains an XSS vulnerability (e.g., a vulnerable third-party NPM package or unsanitized user input), the attacker can execute `localStorage.getItem("token")` to extract the session token. `HttpOnly` cookies cannot be accessed by JavaScript runtime engines.

**Q3. How does Single Sign-On (SSO) work using cookies?**

* **Answer:** By setting a wildcard or parent domain attribute (e.g., `domain: ".company.com"`), the browser includes that cookie in requests sent to any subdomain (`app.company.com`, `admin.company.com`, `api.company.com`). This enables seamless cross-subdomain authentication without re-login.

**Q4. What is the standard size limit for HTTP cookies?**

* **Answer:** Most browsers enforce a limit of approximately **4 KB** per cookie (including name, value, and attributes). Because of this restriction, cookies should store only compact tokens (like JWTs) or unique identifiers, never raw datasets.

## 1. Same-Origin Policy (SOP)

The Same-Origin Policy is a fundamental browser security mechanism that restricts a script loaded from one origin from interacting with resources from another origin. Its purpose is to isolate potentially malicious documents and prevent cross-site data theft.

### Origin Definition (The Triad Rule)

Two URLs share the **same origin** if and only if all three components match:

1. **Protocol / Scheme** (e.g., `http://` vs `https://`)
2. **Host / Domain** (e.g., `api.example.com` vs `example.com`)
3. **Port** (e.g., `:3000` vs `:4000`)

| Target URL (Relative to `[https://cg.com:443/courses](https://cg.com:443/courses)`) | Same Origin? | Reason |
| --- | --- | --- |
| `[https://cg.com/about](https://cg.com/about)` | Yes | Protocol, host, and port match |
| `[http://cg.com/courses](http://cg.com/courses)` | No | Protocol mismatch (`http` vs `https`) |
| `[https://cg.com:8080/courses](https://cg.com:8080/courses)` | No | Port mismatch (`8080` vs `443`) |
| `[https://learn.cg.com/courses](https://learn.cg.com/courses)` | No | Subdomain / host mismatch |

---

## 2. Cross-Origin Resource Sharing (CORS)

CORS is an **HTTP header-based mechanism** that allows a server to explicitly instruct the browser to permit cross-origin requests that would otherwise be blocked by SOP.

* **Key Takeaway:** The browser—not the server—blocks the request. In many cases, the request reaches the backend and executes, but the browser withholds the response from client-side JavaScript if valid headers are absent.
* **Server-to-Server vs. Browser:** CORS does not apply to server-to-server calls or tools like Postman/cURL, because they do not implement browser-level Same-Origin Policy.

---

## 3. Preflight Requests

A preflight request is an automated safety check made by the browser prior to sending the actual cross-origin request. It determines whether the target server recognizes and permits the incoming HTTP method and custom headers.

* **HTTP Method:** `OPTIONS`
* **Browser Request Headers:**
* `Access-Control-Request-Method`: Declares the upcoming method (e.g., `POST`, `PUT`).
* `Access-Control-Request-Headers`: Declares custom headers sent with the actual request (e.g., `Authorization`, `Content-Type`).


* **Server Response:** If the server returns valid matching `Access-Control-Allow-*` headers, the browser fires the primary request.

---

## 4. Simple vs. Non-Simple Requests

The browser categorizes requests into two types to decide whether a preflight (`OPTIONS`) check is required.

### Simple Requests (No Preflight)

Triggered directly without an `OPTIONS` check if **all** the following conditions are met:

1. **Allowed Methods:** Only `GET`, `HEAD`, or `POST`.
2. **Allowed Headers:** Only standard safelisted headers (e.g., `Accept`, `Accept-Language`, `Content-Language`).
3. **Allowed `Content-Type`:** Restricted to:
* `text/plain`
* `multipart/form-data`
* `application/x-www-form-urlencoded`



### Non-Simple Requests (Preflight Mandatory)

An `OPTIONS` preflight request is automatically dispatched if **any** of the following occur:

* Uses methods such as `PUT`, `PATCH`, or `DELETE`.
* Contains non-safelisted request headers (e.g., `Authorization`, custom tokens).
* Uses `Content-Type: application/json` (standard for REST APIs).

---

## 5. Handling Cookies and Credentials

By default, cross-origin requests omit cookies, HTTP authorization headers, and TLS client certificates to protect users against unauthorized credential exposure.

### Two-Way Handshake Requirement

1. **Client-side:**
* `fetch`: `{ credentials: 'include' }`
* `axios`: `{ withCredentials: true }`


2. **Server-side:**
* Response must include: `Access-Control-Allow-Credentials: true`
* **The Wildcard Rule:** When credentials mode is active, the server **cannot** respond with `Access-Control-Allow-Origin: *`. The origin must be explicitly mirrored (e.g., `Access-Control-Allow-Origin: [https://frontend.com](https://frontend.com)`).



---

## 6. Core CORS Response Headers Reference

| Header | Description | Example |
| --- | --- | --- |
| `Access-Control-Allow-Origin` | Lists allowed domain(s) or wildcard. | `[https://app.example.com](https://app.example.com)` |
| `Access-Control-Allow-Methods` | Lists permitted HTTP methods for preflight. | `GET, POST, PUT, DELETE` |
| `Access-Control-Allow-Headers` | Lists permitted request headers. | `Content-Type, Authorization` |
| `Access-Control-Allow-Credentials` | Tells browser to expose response when cookies are sent. | `true` |
| `Access-Control-Max-Age` | Caches preflight result in seconds to prevent repeated `OPTIONS` hits. | `86400` (24 hours) |
| `Access-Control-Expose-Headers` | Exposes specific response headers to client JavaScript. | `X-Total-Count, Content-Range` |

---

## 7. Production Implementation (Express.js)

Applying bare `app.use(cors())` defaults to `Access-Control-Allow-Origin: *`, which exposes APIs to arbitrary client domains and breaks authenticated requests.

```javascript
const express = require('express');
const cors = require('cors');

const app = express();

const whitelist = ['https://myfrontend.com', 'https://admin.myfrontend.com'];

const corsOptions = {
  origin: (origin, callback) => {
    // Allow non-browser requests (e.g., Postman) where origin is undefined
    if (!origin || whitelist.includes(origin)) {
      callback(null, true);
    } else {
      callback(new Error('Blocked by CORS security policy'));
    }
  },
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization'],
  exposedHeaders: ['X-Total-Count'],
  maxAge: 600 // Cache preflight for 10 minutes
};

app.use(cors(corsOptions));

```

## 8. High-Frequency Interview Questions

**Q1: Does CORS prevent CSRF attacks completely?**

* **Answer:** No. CORS is designed to protect resource consumers from unauthorized data access, not to eliminate cross-site request execution entirely. Simple requests (like a `POST` form submit) are still processed by the server before the browser blocks the reading of the response. Robust CSRF mitigation requires **Anti-CSRF tokens** and `SameSite` cookie flags (`Strict` or `Lax`).

**Q2: Why does an API request work in Postman but fail in the browser console?**

* **Answer:** Postman is an HTTP client tool, not a web browser. It does not enforce browser security sandboxing or the Same-Origin Policy. The browser, however, executes scripts in a shared runtime environment and enforces CORS compliance on the responses.

**Q3: Why did a simple `GET` request trigger a preflight `OPTIONS` call?**

* **Answer:** Even though `GET` is a simple method, adding a custom or protected header (such as `Authorization: Bearer <token>`) classifies the request as non-simple, triggering a mandatory preflight validation.

What Happens When We Log In to a Website? — Complete Interview Explanation
For a React Developer interview, this is an important question because it connects HTML forms, JavaScript, React, APIs, HTTP, backend, database, authentication, cookies, sessions, tokens, and protected routes.

Let's understand it step by step using a simple example: you log in to an e-commerce website.

1. The complete login flow
1. User enters email and password

Login form in the browser / React frontend

2. Frontend sends an API request

HTTP POST request over HTTPS

3. Backend validates the credentials

Node.js / Express or another server

4. Backend checks the database

Finds the user and verifies the password hash

5. Server creates an authenticated session

For example, a session ID stored in an HttpOnly cookie

6. User reaches the dashboard

Future protected requests are authenticated

Now let's understand what happens inside each step.

2. Step 1: User enters email and password
Suppose you enter:

Email: sachin@example.com

Password: your password

The frontend collects the input using HTML and JavaScript. In React, we might use state to hold the form values.

const [email, setEmail] = useState("");
const [password, setPassword] = useState("");

When you click Login, the form can validate whether the fields are empty and whether the email format looks correct.

Important: Frontend validation improves user experience, but it is not security. The backend must validate the input again.

3. Step 2: The browser sends an API request
The React frontend sends the entered credentials to the backend.

const response = await fetch("/api/login", {
  method: "POST",
  headers: {
    "Content-Type": "application/json"
  },
  body: JSON.stringify({ email, password })
});

What happens here?

POST sends the login data to the server.

Content-Type tells the server the body contains JSON.

JSON.stringify() converts the JavaScript object into a JSON string.

HTTPS encrypts the request while it travels across the network.

The password is sent to the server for verification; it should never be saved as plain text in the database.

4. Step 3: Backend receives the request
The backend might use Node.js and Express.

app.post("/api/login", async (req, res) => {
  const { email, password } = req.body;

  // Validate input
  // Find user in database
  // Verify password hash
  // Create authenticated session
});

The backend performs checks such as:

Is the input valid?

Does the account exist?

Does the supplied password match the stored password hash?

Is the account permitted to log in?

The backend, not React, makes the final authentication decision.

5. Step 4: Backend checks the database
The backend queries the database, such as MongoDB or MySQL, to find the user.

A user record might look like this:

{
  email: "sachin@example.com",
  passwordHash: "$2b$12$...",
  role: "user"
}

Notice that the database stores a password hash, not the original password.

The backend uses a password-hashing library, such as bcrypt or Argon2, to verify the submitted password against the stored hash.

Correct password → authentication can succeed.

Incorrect password → login fails.

Unknown account → login fails.

Websites commonly return a general message such as "Invalid email or password" to avoid revealing which accounts exist.

6. Step 5: Server creates a session or token
After successful authentication, the server needs a way to recognize you on later requests.

There are two common approaches.

Method A: Session-based authentication

The server creates a session and stores it server-side.
The server sends a session ID in a cookie.
The browser stores the cookie.
The browser sends the cookie with matching requests.
The server looks up the session and identifies the user.
Common secure setup: an HttpOnly, Secure cookie with an appropriate SameSite setting.

Method B: Token-based authentication

The server issues an access token, often a JWT.
The client sends the token with subsequent API requests.
The server validates the token and its claims.
The server checks permissions before returning protected data.
Tokens may be sent in an Authorization header or, depending on the design, stored in cookies. JWT and session-based authentication are not the same thing.

What is a JWT?
JWT stands for JSON Web Token. It commonly consists of three Base64URL-encoded parts:

Header.Payload.Signature

It can contain claims such as a user ID, expiry time, and issuer. A signed JWT is not automatically encrypted, so you should not put secrets in its payload.

7. Step 6: What happens inside the browser after login?
In a cookie-based login, the server might return a response like this:

HTTP/1.1 200 OK
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax; Path=/
Content-Type: application/json
This is an illustrative response, not a real session.

The browser processes the Set-Cookie header and stores the cookie according to its attributes.

Important: If the cookie is HttpOnly, JavaScript cannot read it through document.cookie. The browser can still send it automatically with eligible requests.

The response body might contain:

{
  "success": true,
  "user": {
    "name": "Sachin"
  }
}

The frontend can use the returned user information to update the UI. The server should not rely on the frontend's user object as proof of authentication.

8. Step 7: What happens when you open the dashboard?
Suppose you visit /dashboard.

The frontend might render the dashboard route, but protected data should come from an authenticated API request.

For example:

const response = await fetch("/api/profile", {
  credentials: "include"
});

const profile = await response.json();

With credentials: "include", the browser can send eligible cookies even for cross-origin requests, subject to cookie and CORS policies.

Then:

The browser sends the request.

The server receives the session cookie.

The server validates the session.

The server checks whether the user is authorized to access the requested resource.

The server returns the permitted data or rejects the request.

Authentication means verifying who you are.

Authorization means checking what you are allowed to do.

For example, logging in proves your identity; it does not automatically give you admin access.

# Authorization in Node.js — Interview Notes

Node.js backend interviews mein Authentication vs Authorization, JWT, Middleware, Roles, Cookies, and Protected Routes bahut important topics hain.

## 1. What is Authorization?

Definition: Authorization is the process of checking what a logged-in user is allowed to access or do.

Simple Hinglish: User login kar chuka hai, ab check karna ki woh kaunsa page ya resource access kar sakta hai.

Example:

- User can view their own profile.
- Admin can delete users.
- Normal user cannot access admin routes.

## 2. Authentication vs Authorization ⭐

| Authentication       | Authorization           |
| -------------------- | ----------------------- |
| Who are you?         | What can you access?    |
| Checks user identity | Checks user permissions |
| Login, password, OTP | Roles and permissions   |
| Happens first        | Follows authentication  |

Interview answer: Authentication verifies a user's identity, whereas authorization determines what resources the authenticated user can access.

## 3. How Authorization Works in Node.js

1\. User logs in

Email and password

2\. Server verifies credentials

Creates a session or JWT

3\. Client sends credentials/token

With the protected API request

4\. Authentication middleware

Verifies identity and token

5\. Authorization middleware

Checks role and permissions

Allowed

Controller runs

Denied

403 Forbidden

## 4. What is Middleware?

Middleware is a function that runs during the request-response cycle, before the final route handler or between other handlers.

In Node.js with Express, middleware commonly uses:

- `req` — request data
- `res` — response object
- `next()` — passes control to the next middleware

Example:

```
function checkUser(req, res, next) {
  console.log("Checking user...");
  next();
}
```

Usage:

```
app.get("/profile", checkUser, (req, res) => {
  res.send("Profile page");
});
```

Interview tip: Middleware is used for authentication, authorization, logging, validation, and error handling.

## 5. Role-Based Authorization (RBAC)

RBAC stands for Role-Based Access Control. Access is granted based on the user's role.

Example roles:

- `user`
- `admin`
- `manager`

### Complete Express.js example

```
const express = require("express");
const app = express();

// Authorization middleware
function authorize(...allowedRoles) {
  return (req, res, next) => {
    if (!req.user) {
      return res.status(401).json({
        message: "Please log in"
      });
    }

    if (!allowedRoles.includes(req.user.role)) {
      return res.status(403).json({
        message: "Access denied"
      });
    }

    next();
  };
}
```

Use it on a protected route:

```
app.delete(
  "/users/:id",
  authenticateToken,
  authorize("admin"),
  (req, res) => {
    res.json({ message: "User deleted" });
  }
);
```

Here, `authenticateToken` is assumed to be a previously defined authentication middleware that verifies the token and sets `req.user`.

How it works:

1. `authenticateToken` verifies the user's identity.
2. `authorize("admin")` checks their role.
3. If the role is `admin`, the request continues.
4. Otherwise, the server returns `403 Forbidden`.

Important: In a real application, verify that the user is allowed to delete the particular target user, not just that they have a valid role.

## 6. Authentication using JWT

JWT stands for JSON Web Token. It is a compact token format commonly used to carry signed claims about a user.

Install the package:

```
npm install jsonwebtoken
```

### Create a token

```
const jwt = require("jsonwebtoken");

const token = jwt.sign(
  { id: user._id, role: user.role },
  process.env.JWT_SECRET,
  { expiresIn: "1h" }
);
```

### Verify the token

```
function authenticateToken(req, res, next) {
  const authHeader = req.headers.authorization;

  const token = authHeader?.split(" ")[1];

  if (!token) {
    return res.status(401).json({
      message: "Token required"
    });
  }

  try {
    const decoded = jwt.verify(
      token,
      process.env.JWT_SECRET
    );

    req.user = decoded;
    next();
  } catch (error) {
    return res.status(401).json({
      message: "Invalid or expired token"
    });
  }
}
```

The client typically sends the token like this:

```
Authorization: Bearer your_token_here
```

Remember:

- `jwt.sign()` creates a signed token.
- `jwt.verify()` validates the signature and expiration.
- `req.user` stores the verified claims for later middleware.
- JWT payloads are not encrypted by default. Never put passwords or secrets inside them.
- Keep the secret in environment variables and use HTTPS.

## 7. HTTP Status Codes for Authorization ⭐

| Status | Meaning      | Example                                    |
| ------ | ------------ | ------------------------------------------ |
| `200`  | OK           | Request succeeded                          |
| `401`  | Unauthorized | Missing or invalid login credentials/token |
| `403`  | Forbidden    | Authenticated user lacks permission        |
| `404`  | Not Found    | Resource does not exist                    |

Easy trick: `401` = identity not established; `403` = identity may be established, but access is denied.

## 8. Authorization vs Cookies vs JWT

These concepts are related but different.

| Concept       | Purpose                                                           |
| ------------- | ----------------------------------------------------------------- |
| Authorization | Determines access permissions                                     |
| Cookie        | Stores data in the browser and sends it according to cookie rules |
| JWT           | Carries signed claims                                             |
| Session       | Server-managed login state                                        |
| Middleware    | Checks requests before routes continue                            |

A cookie can contain a session identifier or a JWT. A JWT can also be sent through the `Authorization` header. Cookies and JWTs are not the same thing.

## 9. Frequently Asked Interview Questions

Q1. Can authorization work without authentication?Yes, for public resources or systems using other access mechanisms. However, user-specific authorization commonly follows authentication.

Q2. Where should authorization logic be written?Usually in reusable middleware or a policy/service layer, with checks enforced on the server.

Q3. Can we trust a role sent by the frontend?No. The backend must use trusted, verified information and check permissions server-side.

Q4. What is RBAC?Role-Based Access Control. Permissions are assigned according to roles such as admin, manager, and user.

Q5. What happens if a token expires?Token verification fails, and the server generally returns 401. The client may need to log in again or use a secure refresh-token flow.

Q6. How do you protect an API route?Use authentication middleware, authorization checks, input validation, and appropriate resource ownership checks.

Q7. What is the difference between 401 and 403?401 means valid authentication is missing or not established. 403 means access is not permitted.

## 10. Last-Minute Revision

- Authentication: Who are you?
- Authorization: What can you access?
- JWT: Signed token carrying claims.
- Middleware: Function that checks or processes requests.
- RBAC: Access based on roles.
- 401: Authentication missing or invalid.
- 403: Permission denied.
- `next()`: Continue to the next middleware.
- `jwt.verify()`: Verify token validity.
- Best practice: Never rely on frontend-only authorization.

Interview-ready answer: “In Node.js, I implement authorization using Express middleware. First, authentication middleware verifies the user's session or JWT. Then, authorization middleware checks their role, permissions, and sometimes resource ownership. If the user has permission, the request proceeds; otherwise, the server returns an appropriate error such as 403 Forbidden.”

# 1. Multer — File Upload Middleware

## What is Multer?

Multer is a middleware for Express.js used to handle `multipart/form-data`, mainly for uploading files.

Simple Hinglish: Jab user website par image, PDF, ya koi document upload karta hai, tab backend par file receive aur save karne ke liye Multer use karte hain.

Examples: Profile photo upload, resume upload, document upload.

## Install Multer

```

```

## A. How Multer works

Frontend form

User selects an image

multipart/form-data

Processes the uploaded file

Local folder or memory buffer

## B. Basic Multer code

```
const express = require("express");
const multer = require("multer");

const app = express();

const upload = multer({ dest: "uploads/" });

app.post("/upload", upload.single("image"), (req, res) => {
  console.log(req.file);
  console.log(req.body);

  res.send("File uploaded");
});

app.listen(8000);
```

Here, Multer saves the uploaded file to the `uploads/` directory using a generated filename.

## C. Important Multer methods ⭐

| Method                      | Purpose                                     |
| --------------------------- | ------------------------------------------- |
| `upload.single("image")`    | Upload one file                             |
| `upload.array("images", 5)` | Upload multiple files under one field       |
| `upload.fields([...])`      | Upload files from multiple named fields     |
| `upload.none()`             | Accept only text fields in multipart form   |
| `upload.any()`              | Accept files from any field; use cautiously |

### Examples

Single file

```
app.post("/profile", upload.single("avatar"), (req, res) => {
  console.log(req.file);
  res.send("Done");
});
```

Multiple files

```

  console.log(req.files);
  res.send("Done");
});
```

Multiple named fields

```
app.post(
  "/documents",
  upload.fields([
    { name: "profile", maxCount: 1 },
    { name: "resume", maxCount: 1 }
  ]),
  (req, res) => {
    console.log(req.files);
    res.send("Done");
  }
);
```

## D. `req.file` vs `req.files` vs `req.body`

| Property    | Contains                                      |
| ----------- | --------------------------------------------- |
| `req.file`  | One uploaded file                             |
| `req.files` | Multiple uploaded files                       |
| `req.body`  | Normal text fields, such as username or email |

```

```

  console.log(req.body.username);
  console.log(req.file);
  res.send("Uploaded");
});
```

Important: The file input's `name` must match the name passed to Multer. Here, both are `image`.

## E. Disk storage

Disk storage lets you control where the file is saved and what its filename will be.

```
const path = require("path");
const multer = require("multer");

const storage = multer.diskStorage({
  destination: (req, file, cb) => {
    cb(null, path.resolve("uploads"));
  },

  filename: (req, file, cb) => {
    cb(null, Date.now() + path.extname(file.originalname));
  }
});

const upload = multer({ storage });
```

- `destination`: Directory for uploaded files.
- `filename`: Name used to save each file.
- `file.originalname`: Original name supplied by the client.
- `path.extname()`: Extracts the extension, such as `.jpg`.

Create the `uploads` directory beforehand. For production, generate safe, unique filenames and validate the actual file type; do not trust the extension alone.

## F. File size limits and validation

```
const upload = multer({
  storage,
  limits: {
    fileSize: 2 * 1024 * 1024
  },
  fileFilter: (req, file, cb) => {
    const allowed = ["image/jpeg", "image/png"];

    if (allowed.includes(file.mimetype)) {
      cb(null, true);
    } else {
      cb(new Error("Only JPEG and PNG allowed"));
    }
  }
});
```

This sets a 2 MB size limit and checks the declared MIME type. For real security, verify file contents as well, since MIME types can be spoofed.

## G. DiskStorage vs MemoryStorage

| DiskStorage                     | MemoryStorage                                       |
| ------------------------------- | --------------------------------------------------- |
| Saves files on disk             | Keeps file contents in RAM                          |
| Provides `req.file.path`        | Provides `req.file.buffer`                          |
| Suitable for local file storage | Useful for processing or uploading to cloud storage |
| Needs disk management           | Large uploads can consume significant memory        |

## H. Common Multer errors

- `req.file === undefined`: Wrong field name, no file selected, or file input removed from the DOM.
- `LIMIT_FILE_SIZE`: File exceeded the configured size limit.
- `Unexpected field`: The submitted file field does not match the configured Multer field.
- `ENOENT`: The destination directory does not exist or the path is invalid.

Remember the frontend requirement:

```
<form method="POST" enctype="multipart/form-data">
```
